1. Resumen Ejecutivo

1.1 Descripción del incidente

El 28 de julio de 2026 se reportó que un usuario con rol operador, al iniciar sesión desde el navegador Mozilla Firefox, visualizaba y podía acceder a todos los módulos reservados para administrador: gestión de usuarios, acceso a las 3 tiendas, domiciliación bancaria y actividades pendientes de todas las sedes.

El mismo usuario, al iniciar sesión desde Google Chrome, se comportaba correctamente como operador (solo lectura de su tienda asignada). Esto indica que el bug es dependiente del navegador y no del backend ni de la base de datos.

Clasificación: Escalación de privilegios horizontal/vertical (Privilege Escalation).
Severidad: CRÍTICA — Un operador puede leer datos de cualquier tienda, gestionar usuarios y acceder a funciones de domiciliación bancaria.
Nota importante: El backend sí bloquea operaciones destructivas (POST/PUT/DELETE) con HTTP 403. El riesgo real es la lectura no autorizada de datos de otras tiendas.

2. Análisis de Causas Raíz (Root Cause Analysis)

El bug no tiene una única causa, sino que es el resultado de cuatro fallos simultáneos en el frontend que, combinados, permiten que Firefox muestre privilegios de administrador a un operador.

2.1 Causa 1: Race condition en la inicialización del panel

En panel.js, la función sincronizarPerfilUsuario() es asíncrona y se invoca al inicio del script. Sin embargo, ocultarMenuSegunRol() se ejecuta tanto en el callback de la promesa como en el DOMContentLoaded, creando una condición de carrera:

// panel.js — versión vulnerable v6.7
sincronizarPerfilUsuario().then(() => {
    ocultarMenuSegunRol();   // ← Ejecución A (async, tarda ~200-500ms)
});

// Más abajo en el mismo archivo:
document.addEventListener('DOMContentLoaded', function() {
    setTimeout(() => {
        ajustarVistaMovil(); // ← Esto llama a ocultarMenuSegunRol()
    }, 300);                  // ← Ejecución B (a los 300ms)
});

Por qué Firefox es diferente: Firefox utiliza el motor SpiderMonkey, cuyo manejo del event loop difiere de V8 (Chrome/Edge). En Firefox, las microtareas de promesas (.then()) pueden resolverse después de que los setTimeout con tiempos cortos ya hayan ejecutado. Esto significa que ocultarMenuSegunRol() se ejecuta con datos viejos del localStorage antes de que el perfil sincronizado actualice la variable usuario.

Consecuencia: Si el localStorage contiene rol: "administrador" de una sesión anterior, ocultarMenuSegunRol() usa ese valor antes de que el perfil sincronizado lo sobrescriba. El menú se renderiza con privilegios de admin.

2.2 Causa 2: Fallback a localStorage legacy sin validación

En panel.js, la carga inicial del usuario tiene este fallback:

// panel.js — versión vulnerable v6.7
try {
    let usuarioRaw = localStorage.getItem('usuario');
    if (!usuarioRaw || usuarioRaw === 'undefined' || usuarioRaw === 'null') {
        usuarioRaw = localStorage.getItem('user');  // ← Fallback legacy
    }
    if (usuarioRaw && usuarioRaw !== 'undefined' && usuarioRaw !== 'null') {
        usuario = JSON.parse(usuarioRaw);
    }
} catch (e) {
    usuario = {};
}

El problema es que la clave 'user' es un residuo de versiones anteriores del sistema (anteriores a v6.0). Si un administrador inició sesión en una versión antigua (que usaba 'user'), esa clave puede persistir en el navegador indefinidamente. Cuando un operador inicia sesión y por alguna razón la clave 'usuario' queda vacía o corrupta, el sistema cae en el fallback 'user' que contiene rol: "administrador".

2.3 Causa 3: Decodificación JWT no robusta (base64url)

Los tokens JWT usan codificación base64url, que reemplaza + por -, / por _ y omite el padding =. El código original usaba atob() directamente:

// login.js — versión vulnerable v6.7
const payload = JSON.parse(atob(data.token.split('.')[1]));

Firefox es más estricto que Chrome con atob(): si el payload del JWT contiene caracteres - o _ (muy común) o falta padding, atob() lanza DOMException en Firefox mientras que Chrome a veces lo tolera. Cuando falla, el catch asigna rol: 'operador', pero como la Causa 1 y 2 ya cargaron un usuario con rol de admin desde localStorage, ese fallback nunca se aplica.

2.4 Causa 4: Limpieza incompleta de sesión (logout)

La función cerrarSesion() en panel.js solo eliminaba 'token' y 'usuario', pero no eliminaba la clave legacy 'user' ni 'tienda_usuario':

// panel.js — versión vulnerable v6.7
function cerrarSesion() {
    localStorage.removeItem('token');
    localStorage.removeItem('usuario');
    // ❌ Falta: localStorage.removeItem('user');
    // ❌ Falta: localStorage.removeItem('tienda_usuario');
    window.location.href = '/';
}

Esto significa que aunque el administrador haga logout, los datos de su sesión permanecen en el navegador. Cuando un operador usa la misma máquina/navegador, esos datos fantasmas están disponibles para el fallback.

Diagrama de interacción de causas:
Causa 4 (logout incompleto) → Datos de admin persisten en localStorage
Causa 2 (fallback legacy) → El sistema lee esos datos viejos
Causa 1 (race condition) → El menú se renderiza antes de la sincronización
Causa 3 (JWT falla) → No hay corrección posible desde el token
Resultado: Operador ve menú de administrador

4. Soluciones Implementadas (v6.7.1)

4.1 Fix en public/js/login.js

Problema

Decodificación JWT frágil con atob() directo; no se limpian datos antiguos antes de guardar la nueva sesión.

Solución

  1. Helper decodeJWT(): Convierte base64url a base64 estándar, agrega padding si falta, y maneja errores silenciosamente. Compatible con SpiderMonkey (Firefox) y V8 (Chrome/Edge).
  2. Limpieza previa: Antes de guardar la nueva sesión, se eliminan todas las claves relacionadas (token, usuario, user, tienda_usuario).
  3. Fuente de verdad: El rol se extrae primero del token JWT (firmado por el backend), no de la respuesta JSON del login.
function decodeJWT(token) {
    try {
        const base64Url = token.split('.')[1];
        const base64 = base64Url.replace(/-/g, '+').replace(/_/g, '/');
        const pad = base64.length % 4;
        if (pad) {
            const padded = base64 + '='.repeat(4 - pad);
            return JSON.parse(atob(padded));
        }
        return JSON.parse(atob(base64));
    } catch (e) {
        console.warn('Error decodificando JWT:', e);
        return null;
    }
}

// En el handler de login exitoso:
localStorage.removeItem('token');
localStorage.removeItem('usuario');
localStorage.removeItem('user');
localStorage.removeItem('tienda_usuario');
localStorage.setItem('token', data.token);

const payload = decodeJWT(data.token);
const rolFinal = payload?.rol || data.usuario?.rol || 'operador';

4.2 Fix en public/js/panel.js

Problema

Race condition entre sincronización de perfil y renderizado del menú; fallback a 'user' legacy; getUserRole() prioriza localStorage sobre el token JWT.

Solución

  1. Jerarquía de fuentes: getUserRole() y getTiendaUsuario() priorizan el token JWT (firmado, inmutable) sobre localStorage (mutable por el usuario o extensiones).
  2. Inicialización síncrona: Al cargar panel.js, se decodifica el token inmediatamente para tener el rol correcto antes de cualquier operación asíncrona.
  3. Secuencialización: sincronizarPerfilUsuario() se ejecuta de forma secuencial (con await) antes de llamar a ocultarMenuSegunRol().
  4. Validación de discrepancias: Si el rol del backend difiere del token, se loggea en consola pero se usa el del token (más confiable).
  5. Manejo de errores robusto: Si la sincronización falla, se usa el rol del token como fallback seguro. Si no hay token, se fuerza logout.
function getUserRole() {
    const token = localStorage.getItem('token');
    if (token) {
        const payload = decodeJWT(token);
        if (payload && payload.rol) return payload.rol;
    }
    // Fallback a localStorage solo si no hay token
    const userData = localStorage.getItem('usuario');
    if (userData) {
        try { return JSON.parse(userData).rol; } catch (e) {}
    }
    return 'operador';
}

// Inicialización secuencial con manejo de errores
(async function initSeguridad() {
    try {
        await sincronizarPerfilUsuario();
    } catch (e) {
        console.error('Error sincronizando perfil:', e);
        const token = localStorage.getItem('token');
        if (!token || !decodeJWT(token)) {
            cerrarSesion();
            return;
        }
    }
    ocultarMenuSegunRol();
    ajustarVistaMovil();
})();

4.3 Fix en cerrarSesion()

Problema

No se eliminaban las claves legacy 'user' y 'tienda_usuario', ni 'seccion_actual'.

Solución

function cerrarSesion() {
    const t = localStorage.getItem('token');
    if (t) {
        fetch('/api/auth/logout', {
            method: 'POST',
            headers: { 'Authorization': 'Bearer ' + t },
            keepalive: true
        }).catch(() => {});
    }
    localStorage.removeItem('token');
    localStorage.removeItem('usuario');
    localStorage.removeItem('user');          // ← NUEVO: elimina legacy
    localStorage.removeItem('tienda_usuario'); // ← NUEVO
    localStorage.removeItem('seccion_actual'); // ← NUEVO
    window.location.href = '/';
}
Resultado del fix v6.7.1: Tras aplicar los cambios, un operador que inicie sesión en Firefox después de que un administrador haya usado el mismo navegador ya no hereda privilegios de admin. El menú se filtra correctamente y el dashboard muestra solo la tienda asignada.

5. Vulnerabilidades Residuales (Honestidad Técnica)

El fix v6.7.1 resuelve el bug de escalación de privilegios en el frontend, pero no elimina todas las debilidades arquitectónicas del sistema. A continuación se documentan las vulnerabilidades residuales que persisten y requieren atención en versiones futuras.

IDVulnerabilidadSeveridadExplotabilidadFix en v6.7.1

VR-02Backend no filtra lectura (GET) por tienda. Un operador con token válido puede hacer GET /api/tiendas/maracay y leer todos los clientes de otra tienda. El middleware soloSuTienda existe pero no se aplica en todos los endpoints GET.AltaAltaNo
VR-03Falta validación de iss/aud en JWT. El token no valida emisor (iss) ni audiencia (aud), permitiendo potencialmente reuso de tokens de otros entornos.MediaBajaNo

VR-05Sin logging de discrepancias de rol. Si un token con rol "admin" llega al backend pero el usuario fue degradado a "operador", no hay registro de auditoría del intento.MediaBajaNo

Advertencia: El fix v6.7.1 es un parche de emergencia que corrige el síntoma (frontend muestra menú de admin a operador en Firefox) pero NO corrige la causa raíz arquitectónica: la autenticación basada en localStorage es inherentemente vulnerable a XSS y manipulación. Se recomienda planificar una versión v6.8 con migración a cookies HttpOnly; Secure; SameSite=Strict.

Explicación técnica de VR-02 (lectura no autorizada)

El middleware soloSuTienda existe en middleware/auth.js y se aplica en las rutas paramétricas de tiendas:

// routes/tiendas.js — rutas paramétricas (SÍ protegidas)
router.get('/:tienda', verificarToken, validarTienda, listarClientes);

Sin embargo, el middleware validarTienda aplica la restricción. El problema es que no todos los endpoints GET del sistema usan este middleware. Por ejemplo, endpoints legacy o endpoints de reportes/estadísticas pueden no tener la protección de tienda aplicada consistentemente. Además, un operador con token válido puede hacer:

fetch('/api/tiendas/maracay', {
    headers: { 'Authorization': 'Bearer ' + token }
});

Y el backend sí devolverá los datos si el token es válido, porque verificarToken solo valida que el usuario exista y esté activo, pero no que el operador solo pueda leer su tienda. La restricción de tienda está en validarTienda, que se aplica en las rutas paramétricas, pero debe auditarse en todos los endpoints GET.

7. Recomendaciones Arquitectónicas a Futuro

7.1 Migración de localStorage a cookies HttpOnly

El problema fundamental es que localStorage es accesible por JavaScript. Cualquier vulnerabilidad XSS (Cross-Site Scripting) o extensión maliciosa puede leer el token y suplantar al usuario.

Arquitectura propuesta para v6.8:

┌─────────────────────────────────────────────────────────────┐
│  CLIENTE (Navegador)                                        │
│  ┌─────────────────────────────────────────────────────┐   │
│  │  localStorage: SOLO estado de UI (temas, filtros)   │   │
│  │  Cookie HttpOnly: token JWT (inaccesible por JS)    │   │
│  └─────────────────────────────────────────────────────┘   │
│                              │                              │
│                              ▼                              │
│  Cada petición /api/ envía la cookie automáticamente      │
│  (el navegador lo hace, no el código JS)                    │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  SERVIDOR (Node.js / Express)                               │
│  ┌─────────────────────────────────────────────────────┐   │
│  │  Middleware verificarToken:                          │   │
│  │  1. Lee cookie "jwt" (no header Authorization)      │   │
│  │  2. Valida firma + expiración                       │   │
│  │  3. Valida iss + aud                                │   │
│  │  4. Valida token_version vs BD                      │   │

│  │  CADA endpoint GET filtra por req.usuario.tienda    │   │

│  └─────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘

Implementación en Express:

// server.js — configuración de cookies
const cookieParser = require('cookie-parser');
app.use(cookieParser());

// Login: enviar token como cookie HttpOnly

    httpOnly: true,
    secure: process.env.NODE_ENV === 'production',
    sameSite: 'Strict',
    maxAge: 8 * 60 * 60 * 1000 // 8 horas
});

// Middleware verificarToken: leer de cookie
const verificarToken = async (req, res, next) => {
    const token = req.cookies?.jwt || req.header('Authorization')?.replace('Bearer ', '');
    // ... resto de la validación
};

7.2 Autorización fina en el backend (Row-Level Security)

La restricción de tienda no debe depender de que el desarrollador "se acuerde" de poner el middleware. Debe ser obligatoria por diseño:

// Middleware universal para TODAS las rutas de tiendas
function restringirATiendaPropia(req, res, next) {
    if (req.usuario.rol === 'administrador') return next();

    const tiendaSolicitada = req.params.tienda || req.body.tienda || req.query.tienda;
    if (tiendaSolicitada && tiendaSolicitada !== req.usuario.tienda) {
        // Loggear intento de acceso no autorizado
        registrarAuditoria(..., 'ACCESO_TIENDA_DENEGADO', ...);
        return res.status(403).json({ error: 'No tiene acceso a esta tienda' });
    }
    next();
}

// Aplicar a TODAS las rutas de tiendas
app.use('/api/tiendas', verificarToken, restringirATiendaPropia);

7.3 Revocación de sesiones con token_version

El backend ya tiene token_version en la tabla usuarios (v6.1). Se debe validar en cada petición:

// En verificarToken (ya implementado parcialmente)
if (usuarioDb.token_version !== undefined) {
    const tvToken = decoded.tv || decoded.token_version || -1;
    if ((usuarioDb.token_version || 0) !== tvToken) {
        return res.status(401).json({ 
            error: 'Sesion invalidada. Inicie sesion nuevamente.' 
        });
    }
}

7.4 Content Security Policy (CSP)

// server.js — headers de seguridad
app.use((req, res, next) => {
    res.setHeader('Content-Security-Policy', 
        "default-src 'self'; " +
        "script-src 'self'; " +
        "style-src 'self' 'unsafe-inline'; " +
        "img-src 'self' data:; " +
        "connect-src 'self'"
    );
    res.setHeader('X-Content-Type-Options', 'nosniff');
    res.setHeader('X-Frame-Options', 'DENY');
    res.setHeader('Referrer-Policy', 'strict-origin-when-cross-origin');
    next();
});
Nota sobre CSP: La directiva script-src 'self' bloquea inline scripts. Si el sistema usa inline scripts (como los que existen en index.html o handlers onclick), deben migrarse a archivos .js externos antes de aplicar CSP estricto.

            console.log('  token_version (tv):', payload.tv || 'NO PRESENTE');

            if (typeof getUserRole === 'function') {
                const detected = getUserRole();
                console.log('%cComparación de roles:', 'color:#d69e2e;font-weight:bold');
                console.log('  Rol en JWT:', payload.rol);
                console.log('  Rol detectado por getUserRole():', detected);
                console.log('  Coinciden:', payload.rol === detected ? '✅ SÍ' : '🔴 NO (BUG!)');
            }
        } catch (e) {
            console.error('🔴 Token corrupto o inválido:', e.message);
        }
    } else {
        console.warn('⚠️ No hay token en localStorage');
    }

    if (usuario && usuario !== 'undefined') {
        try {
            const u = JSON.parse(usuario);
            console.log('%clocalStorage "usuario":', 'color:#3182ce;font-weight:bold');
            console.log('  Rol:', u.rol);
            console.log('  Tienda:', u.tienda);
        } catch (e) {
            console.error('🔴 localStorage "usuario" corrupto');
        }
    }

    console.log('%c=== FIN DIAGNÓSTICO ===', 'color:#1a3a5c;font-weight:bold;font-size:14px');
})();
